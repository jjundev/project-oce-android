# 턴 피드백 eval 하네스

`feedback.slim` / `feedback.deep`의 출력을 골든 케이스 세트로 반복 측정한다.
실제 Vertex AI를 호출하므로 **쿼터를 소모한다** — jest 스위트(`npm test`)와는 완전히 분리되어 있다.

## 구성

| 위치 | 역할 |
| --- | --- |
| `src/eval/cases.ts` | 골든 케이스 14개(6 카테고리). 순수 데이터 |
| `src/eval/validate.ts` | 구조 검증기. 순수 함수, `npm test`로 오프라인 검증됨 |
| `eval/run.js` | 실 호출 러너. 마크다운 리포트를 `eval/out/`에 쓴다(gitignore) |

## 실행

```bash
GEMINI_API_KEY=$(firebase functions:secrets:access GEMINI_API_KEY) \
  npm run eval -- --temps=0,0.3,0.7 --repeats=3 --task=feedback
```

키를 파일에 쓰거나 커밋하지 말 것 — 환경변수로만 전달한다.

### 플래그

| 플래그 | 기본값 | 설명 |
| --- | --- | --- |
| `--temps` | `0,0.3,0.7` | 스윕할 temperature 목록 |
| `--repeats` | `3` | 케이스·온도당 반복 호출 수. 점수 분산 측정에 쓰인다 |
| `--task` | `feedback` | `feedback` 또는 `feedbackDeep` |
| `--only` | (전체) | 케이스 id를 콤마로. 예: `--only=ag-coffee-please,tg-past-tense` |

호출 수 = 케이스 × 온도 × 반복. 기본값이면 14 × 3 × 3 = 126회. 호출 사이에는 짧은 지연이 있고
(`CALL_DELAY_MS`), HTTP 429/5xx는 1회 재시도된다(그 외 4xx는 결정적 오류로 보고 즉시 실패) — 쿼터
버스트가 스윕 중간에 일부 셀만 조용히 망가뜨리는 것을 막기 위함이다.

## 리포트 읽는 법

1. **요약 표** — 온도별 호출/실패/위반 집계.
   - `전송 실패` / `파싱 실패`는 분리되어 있다: 전송 실패는 재시도 후에도 실패한 HTTP 호출(quota
     burst 등 인프라 문제), 파싱 실패는 응답은 왔지만 `JSON.parse`가 실패한 경우다.
     **파싱 실패가 production에서 실제로 벌어질 숫자다** — production 스트리밍 경로
     (`feedback.ts` / `feedback-deep.ts`)에는 복구(repair) 단계가 없다(복구는
     `generateOnce` 단발 호출 전용, `gemini.ts`). "JSON이 온도가 오를수록 덜 유효해진다"는
     스윕이 잡아내야 할 가장 전형적인 결과이므로, 이 열을 `call-failed`와 뭉뚱그리지 않는다.
   - `검증됨`은 전송·파싱 모두 성공해 구조 검증까지 돌린 호출 수다. 온도별로 이 숫자가 다르면
     표본 크기가 다르다는 뜻이니 점수 스프레드를 그대로 비교하면 안 된다.
   - `구조 위반`과 `기대치 불일치`도 분리되어 있다. `구조 위반`은 모델이 하드 룰을 어긴 진짜
     결함(색상 누출, 스키마 위반, 섹션 순서 뒤바뀜 등)이고, `기대치 불일치`는 각 케이스의
     `expect.*`(예: `noIncorrectSegments`, `scoreMin`)가 실패한 것이다. 이건 채점 결과에 대한
     **주관적 판단**이고 일부는 설계상 논쟁의 여지가 있다(예: `ab-possible-to-sit`는 과잉 교정이
     아니라고 보지만, 그 자체가 논쟁 가능한 주장이다) — 그래서 모든 온도에서 상수처럼 반복 발생할
     수 있고, 구조 위반과 합치면 온도가 실제로 만들어내는 신호가 묻힌다. 사람이 판단할 몫이지
     "깨졌다"로 읽으면 안 된다.
   - `점수 스프레드` = 같은 입력을 반복 호출했을 때 나온 점수의 최대-최소 차이. 피드백은
     채점이므로 이 값이 작을수록 좋다. **`feedbackDeep`에는 점수가 없으므로 항상 `n/a`다** —
     deep에서 온도를 고르는 지표는 이 표의 위반율(`구조 위반` · `기대치 불일치`)이다. 특히
     스키마가 강제하지 않고 프롬프트로만 요구하는 카디널리티 규칙(`toneStyle.levels` 정확히
     5개, `paraphrasing` 정확히 3개, `venn.items` 1-3개)이 온도 상승에 가장 먼저 깨진다.
     `FEEDBACK_TEMPERATURE`는 slim 증거로부터 고른 값을 deep과 공유하며, deep 리포트는 그 값이
     deep에서 위반을 늘리지 않는지 확인하는 용도다.
2. **케이스별 점수**(slim만) — 같은 입력의 반복 점수가 나란히 찍힌다. 흔들리는 케이스가 바로 보인다.
3. **레벨 민감도(level-variance)** — `lv-starter`/`lv-expert`(영어 문장 동일, `level`만 다름)를
   스윕의 **가장 낮은 온도**에서 나란히 보여준다. 더 높은 온도에서의 차이는 레벨 인지가 아니라
   샘플링 노이즈와 뒤섞이므로(confound), "두 출력이 비슷하다 → 레벨 인지 채점이 없다"는 결론은
   가장 낮은 온도에서만 유효하다.
4. **위반 목록** — 기계가 잡은 것 전부(구조 위반, 기대치 불일치, 전송/파싱 실패). 파싱 실패는
   바로 아래 **파싱 실패 원문** 섹션에 응답 원문(최대 500자)이 보존되어 있다 — 무엇이 깨졌는지
   실제로 눈으로 볼 수 있다.
5. **사람이 읽을 출력** — 구조 검증이 닿지 못하는 것, 즉 *이 교정이 학습자에게 실제로 옳은가*를 눈으로 판정하는 구역. 각 케이스의 `note`가 무엇을 봐야 하는지 알려준다.

특히 `already-good` 카테고리를 먼저 볼 것 — 고칠 게 없는 문장에 억지 교정을 만들어내는지가 가장 잘 드러난다.
